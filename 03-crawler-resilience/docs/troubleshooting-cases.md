# 크롤러 유지보수 트러블슈팅 사례집

커뮤니티 수집 크롤러를 운영하며 처리한 대표 사례를 문제→분석→해결→결과 형식으로 정리했습니다. 크롤링 대상 사이트는 모두 익명화(커뮤니티 A/B/C…)했으며, 실제 사내 코드가 아닌 적용 방식 위주의 설명입니다.

---

## 사례 1. SPA 개편으로 무너진 셀렉터 복구 (가장 임팩트 큼)

**문제**
한 커뮤니티가 서버렌더링 방식에서 SvelteKit/shadcn 기반 SPA로 전면 개편됐다. 개편 후 기존 클래스 기반 셀렉터가 전부 깨져 제목·본문·작성일 수집이 실패했다. 특히 빌드마다 `svelte-a1b2c3` 형태의 해시 클래스가 새로 생성돼, 클래스를 다시 맞춰도 다음 배포에서 또 깨지는 구조였다.

**분석**
- 해시 클래스는 근본적으로 신뢰할 수 없는 셀렉터라는 점을 확인.
- 반면 페이지에 `application/ld+json`(구조화 데이터)과 `og:` 메타태그, `data-slot`·id 접미사 같은 **빌드에 의존하지 않는 요소**가 남아 있음을 발견.
- 크롤러 요청이 영문 로케일로 렌더되어 날짜가 `AM/PM`으로 오는 부수 문제도 확인.

**해결**
- 값마다 **다단계 폴백 체인**을 설계: JSON-LD → 메타태그 → 안정 셀렉터 → 정규식.
- 해시 클래스는 셀렉터에서 완전히 배제.
- 본문은 게시판별 접두어가 붙는 id를 접미사 매칭(`id$=post-content`)으로 흡수.
- 날짜 파서를 오전/오후·AM/PM·ISO 8601 모두 대응하도록 통일.

**결과**
개편 후에도 수집이 유지되고, 이후 재배포로 클래스가 또 바뀌어도 셀렉터가 깨지지 않는 구조를 확보. 개편 때마다 반복하던 수동 대응 부담을 구조적으로 줄였다.

## 사례 2. 구조화 데이터(JSON-LD) 우선 추출로 안정성 확보

**문제**
여러 사이트에서 화면 마크업이 조금만 바뀌어도 본문·날짜 추출이 실패했다. HTML 태그 위치에만 의존하는 방식의 한계였다.

**분석**
상당수 사이트가 SEO 목적으로 `application/ld+json`에 제목·본문·작성일·댓글수를 이미 담고 있었다. 이 데이터는 화면 디자인이 바뀌어도 잘 유지된다는 점에 주목했다.

**해결**
- JSON-LD를 1순위 소스로 채택. 배열/단일 객체를 모두 처리하고, `@type`이 `Article`·`DiscussionForumPosting` 등인 노드를 선별.
- 깨진 JSON은 조용히 건너뛰고 다음 후보로 폴백.
- 댓글수는 `comment[]` 배열이 잘려 담기는(truncated) 경우가 있어, 신뢰하지 않고 집계 필드 `interactionStatistic(CommentAction)`만 사용.

**결과**
마크업 변경에 대한 내성이 크게 향상. 이후 유사 사이트를 추가할 때도 같은 패턴을 재사용해 대응 시간을 단축했다.

## 사례 3. 게시판 추가에 따른 URL 패턴 확장

**문제**
수집 대상에 게시판을 추가하거나 사이트가 URL 체계를 바꿀 때마다, 목록·게시글 URL을 구분하는 정규식을 수정해야 했다.

**분석**
케이스가 반복적이었다. (1) 한 사이트에 게시판 하나 편입 → OR 분기 추가, (2) 개편으로 쿼리스트링 URL이 path 기반으로 변경, (3) 게시글 링크의 꼬리 파라미터로 같은 글이 중복 수집.

**해결**
- 목록/게시글 판별 정규식을 **사이트별 레지스트리**로 모아 관리. 게시판 추가 = 규칙 한 줄 추가.
  - 예) `.../pt?page=N` → `.../(pt|name)?page=N`
  - 예) `id=fun&page=N` → `id=(fun|news2)&page=N`
- 게시글 URL은 쿼리스트링을 절단하고 상대경로를 정규화해 **중복 수집 제거**.
- 느슨하던 게시글 정규식을 명시적으로 좁혀(`.*-\d+` → `[^?]+` 등) 오탐을 줄임.

**결과**
게시판 추가·사이트 개편 대응이 규칙 등록만으로 가능해져 유지보수 비용이 감소. 중복 수집으로 인한 데이터 품질 저하도 완화했다.

## 사례 4. 지저분한 실데이터 정규화

**문제**
사이트마다 날짜·조회수 표기가 제각각이라, 수집값이 그대로 저장되면 후속 분석에서 정합성이 깨졌다.

**분석**
- 날짜: `2026.04.26 (일) 15:54`, `2026-03-09T15:17:00+09:00`, `2026년 3월 9일 오후 3:17` 등 혼재.
- 조회수/댓글수: `조회 1,649`, `조회수 42`처럼 콤마·라벨이 섞이고, 값이 없을 때 빈 문자열/NaN 발생.

**해결**
- 날짜를 `YYYY-MM-DD HH:MM:SS` 단일 포맷으로 통일하는 파서 작성(오전/오후·AM/PM·타임존 처리 포함).
- 숫자는 비숫자 문자를 제거하고, 빈 값/NaN은 0으로 방어.

**결과**
수집 데이터의 포맷이 일관돼 후속 분석·적재의 안정성이 향상됐다.

## 사례 5. 외부 수집기 장애 시 대체 소스 전환 (failover)

**문제**
특정 지표(예: 외부 채널의 구독자 수)를 외부 수집기에 의존해 가져오던 중, 해당 외부 수집기에 장애가 발생해 수집이 중단됐다.

**분석**
- 단일 외부 소스에 의존하는 구조라 그 소스가 죽으면 지표 자체가 비는 것이 문제.
- 동일 지표를 얻을 수 있는 대체 수집 경로가 존재함을 확인.

**해결**
- 외부 수집 사이트를 대체 소스로 전환하고, 해당 지표 수집용 목록 화면 템플릿을 그에 맞게 수정.
- 전환 이후 정상 수집 여부를 모니터링으로 확인.

**결과**
외부 수집기 장애 상황에서도 지표 수집을 재개. 단일 소스 의존의 위험을 실제 대응으로 완화했다.

**배운 것**
외부에 의존하는 수집 지표는 대체 경로를 염두에 둔 설계가 필요하다. 장애는 내 코드가 아니라 외부에서 온다.

---

## 이 작업들이 보여주는 것

개별 사이트를 그때그때 고치는 대신, **변화에 견디는 구조를 설계**해 반복 장애 자체를 줄이는 방향으로 접근했습니다. 외부 시스템(사이트)의 변화라는 통제 불가능한 조건 위에서 안정성을 확보하는 문제였고, 이는 운영 시스템의 장애 대응·데이터 품질 관리와 직접 맞닿아 있습니다.
